# MP2 · Evaluated and registered model

| | |
|---|---|
| **After** | [Module 09](../../modules/09-model-registry/index.md) |
| **Integrates** | Modules 06–09 |
| **Effort** | About 8 hours |
| **Weight** | 10% (illustrative) |
| **Assumes MP1** | A clean clone reproduces the baseline |

---

## Brief

Promote one model to `champion`, and prove that a worse one cannot get there. The
second half is the assessment. Anyone can point an alias at their best run;
the skill is defining gates before the results and showing a failing candidate
being stopped by code.

You will also have to defend a choice the aggregate metric cannot make: which
slice matters, and what you are willing to lose in exchange.

---

## Deliverables

1. **Six tracked runs**, each with parameters, metrics, data version, and run ID.
2. **Evaluation report** with at least two slice dimensions and a selection rule
   written before the results.
3. **Registry** with at least three versions and an alias history (`champion`
   moves at least once, and back once).
4. **Promotion policy** with three measurable gates, implemented and executable.
5. **Blocked-promotion log**: the failing candidate, the policy output, and the
   fixed run that passes.
6. **Timed rollback record**: from decision to a prediction served by the previous
   version.

---

## Acceptance criteria

- [ ] Every claim in the report traces to a run ID.
- [ ] The failing candidate is blocked by the policy check, not by a person.
- [ ] Rollback is demonstrated and timed, under five minutes.
- [ ] The report names one slice where the aggregate winner is worse, or states
      with evidence that no such slice exists among those tested.
- [ ] The policy is checked in CI or by a command with a non-zero exit code.
- [ ] The alias history shows at least one promotion and one rollback.

---

## Evidence

| Claim | Weak | Strong |
|---|---|---|
| The gate works | "Policy says AUC > 0.7" | The candidate's metrics, the gate output, and the non-zero exit code |
| The model is better | One aggregate number | Baseline vs candidate on the same split, with slice counts |
| Rollback works | "We can redeploy" | A timestamped log: decision, alias change, served prediction, elapsed time |
| The selection was fair | "We picked the best" | The rule, its file date, and the runs it was applied to |

---

## Rubric

| Criterion | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **Evaluation depth** | One number | Two metrics, no slices | Slices with counts and a decision rule | As level 2, plus a named trade-off and its justification |
| **Registry discipline** | No versions | Versions exist, alias manual and unexplained | Three versions, alias history, immutable artifacts | As level 2, plus a timed rollback and the evidence it served |
| **Gate implementation** | Document only | Script exists, not enforced | Enforced by exit code, blocking is demonstrated | As level 2, plus the gate applied in CI and a fixed run passing |
| **Honesty** | Overclaims | Some limits stated | Aggregate and slice results reported together | As level 2, plus the cost of the chosen trade stated plainly |

---

## Build order

1. Freeze the split and compute the baseline. Write the selection rule.
2. Run six configurations that differ in one thing each.
3. Compute slices; find where the winner is weak.
4. Write the policy; implement it as a script that exits non-zero.
5. Register versions; promote the winner; record the alias.
6. Construct a deliberately weaker candidate; show it blocked.
7. Roll back, timed, and keep the log.

If time is short, do 1, 3, 4, and 7. The gate and the rollback are the assessment.

---

## Common failures

| Failure | Signature | Fix |
|---|---|---|
| Selection rule invented afterwards | "We always intended to weight late trips" | Timestamp the rule in a file before runs |
| Gate that cannot fail | Baseline regenerated by the same run | Pin the baseline by run ID and hash |
| Slice with 4 rows | A dramatic difference that is noise | Report the count; require a minimum |
| Rollback untested | Alias moves, service still serves the old image | Verify the served version at `/model-info` |
| Registry trusted over the artifact | Metrics edited in JSON | Recompute on load, or verify the model hash |

---

## Extension

Add a fourth gate on calibration or prediction distribution, and justify it. A
model can improve ranking while its probabilities drift away from observed rates,
which matters wherever a threshold is used to decide something.

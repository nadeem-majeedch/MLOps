# Projects and Mini-Projects

Reading and labs give you pieces. Projects are where the pieces have to work together.

There are four core mini-projects, one after each natural integration boundary, an optional fifth for the operational half of the job, and one capstone that removes the scaffolding entirely. They all extend the same `raviride-eta` system; nothing is built twice.

## Why projects, when there are already labs

A lab tells you what to do. A project tells you what must be true, and leaves the route to you. That difference is the skill employers pay for, and it is not developed by following instructions more carefully.

Each mini-project is assessed against a rubric, with acceptance criteria written as things an outsider can check in ten minutes.

## The four mini-projects

### MP1 - Reproducible training package

**After:** Module 05 · **Effort:** about 8 hours · **Weight:** 10

**Brief.** A colleague clones your repository on a different machine and must obtain your reported metric without asking you anything.

**What you hand in**

1. Repository with a pinned environment and one documented install command.
2. DVC-tracked dataset with provenance.
3. Stage graph for prepare, featurise, train, evaluate.
4. `metrics.json` plus a two-run comparison showing identical results.
5. A `README` section a stranger can follow.

**Acceptance criteria**

- A clean directory installs and trains using only documented commands.
- Two clean runs agree within a tolerance you stated *before* running.
- Changing one hyperparameter invalidates only the affected stages, shown by logs.
- No absolute paths, no committed datasets, no secrets.

**Typical failure:** it works because of an untracked file in the working directory. Clone to a new folder before submitting.

### MP2 - Evaluated and registered model

**After:** Module 09 · **Effort:** about 8 hours · **Weight:** 10

**Brief.** Promote one model to `champion`, and prove a worse one cannot get there.

**What you hand in**

1. Six tracked runs with parameters, metrics, and dataset version.
2. Evaluation report with at least two slice dimensions and a decision rule.
3. Registry with at least three versions and alias history.
4. Promotion policy with three measurable gates, implemented.
5. Blocked-promotion log and a timed rollback record.

**Acceptance criteria**

- Every claim in the report traces to a run identifier.
- The failing candidate is blocked automatically, not by convention.
- Rollback is demonstrated and timed.
- The report names one slice where the aggregate winner is worse.

**Typical failure:** selecting on the aggregate metric, then discovering the regression during the capstone.

### MP3 - Served, containerised, gated service

**After:** Module 12 · **Effort:** about 12 hours · **Weight:** 10

**Brief.** A caller can get a validated prediction from a container, and CI refuses a regression.

**What you hand in**

1. `/health`, `/predict`, `/model-info` with schema validation.
2. Contract test comparing serving features with training features.
3. Dockerfile with pinned base, non-root user, and `.dockerignore`; size comparison.
4. Compose file running the API beside the tracking store.
5. CI workflow: lint, tests, data validation, smoke train, metric gate, artefact upload.

**Acceptance criteria**

- Five malformed payloads each return 422 with a specific message.
- p95 latency is measured against a budget you defined.
- The image builds from scratch.
- CI fails on a data-schema break, a unit regression, and a metric regression - each for the stated reason.

**Typical failure:** a gate that passes because the baseline file was regenerated by the same failing run. Pin the baseline.

### MP4 - Monitored lifecycle

**After:** Module 14 · **Effort:** about 12 hours · **Weight:** 10

**Brief.** The system notices its own degradation and proposes a retrain, with evidence.

**What you hand in**

1. Drift reports per batch across four replayed weeks.
2. Thresholds with justification, and an alert with an owner and first diagnostic step.
3. A retraining trigger that is conditional.
4. Before/after comparison showing improvement on the affected slice, and no regression elsewhere.
5. A one-page decision memo for a non-technical manager.

**Acceptance criteria**

- Data drift is distinguished from prediction drift in the report.
- The alert fires on the injected drift batch and not before it.
- Retraining is justified by evidence, and a guardrail prevents auto-promotion of a worse model.
- The memo states the cost of retraining and the cost of not retraining.

**Typical failure:** thresholds chosen to look strict, producing an alert on every batch - which is the same as no alert.

### MP5 - Operate and hand over (optional extension)

**After:** Modules 13–16 · **Effort:** about 14 hours · **Weight:** not in the default total

**Brief.** Someone else operates your system for a week while you watch, with only
the runbook. Scheduled retraining, threat model, security evidence, capacity
estimate, a tested handover drill, and an incident review. No paid cloud account
is required; Kubernetes remains optional and is labelled untested if you cannot
run it.

This one exists for students who take the operational modules and want that work
assessed rather than only read. It is the closest rehearsal for the capstone.

## How mini-projects are marked

Each is worth 10. Four criteria per project, scored 0-3 (absent, inadequate, adequate, strong), then scaled. The full descriptors and the worked example are in the [assessment framework](../syllabus/assessment-framework.md#42-worked-example-mp3-served-containerised-gated-service).

| Score | Meaning |
|---|---|
| 0 | Absent or does not run |
| 1 | Present but does not achieve the stated behaviour, or works by accident |
| 2 | Achieves the behaviour, with one significant gap in evidence or robustness |
| 3 | Achieves the behaviour, is robust to a stated perturbation, and would convince a sceptical reviewer |

Polish is not a criterion. Reproducibility, evidence, and honesty are.

## What every project has in common

- **One system.** The same repository grows; new folders are not new projects.
- **Stable paths.** `src/raviride/`, `dvc.yaml`, `Dockerfile`, `.github/workflows/ci.yml`. Later modules modify these files rather than creating parallel copies.
- **Evidence over narrative.** A claim without a log, a metric, or a run identifier is not evidence.
- **Honesty about limits.** Every project asks what it does not do, and marks it.

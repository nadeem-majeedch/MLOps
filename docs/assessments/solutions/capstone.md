# Capstone reference notes

> **Reference only.** This page describes what a strong submission tends to
> contain and where the working examples are. It is not a model answer to copy:
> the capstone is assessed on your system and your evidence.

The brief is [here](../../projects/capstone.md); the rubric and self-marking
procedure are in the [capstone assessment](../capstone-assessment.md).

---

## 1. The shape of a strong submission

It is smaller than most students expect:

```text
one model, one service, one gate, one alert, one runbook,
seven pieces of evidence, and a defence that admits one gap
```

Strong submissions share five properties, and none of them is technical novelty:

1. **The README states the limitation before the feature list.** A reader knows
   what not to expect.
2. **The failing runs are kept.** The CI evidence includes a red run for each
   injected defect, with the failing step named.
3. **The gate's baseline is pinned.** Re-running the baseline is a separate,
   deliberate act.
4. **The runbook was tested on a person**, and the questions they had to answer
   alone are listed as findings.
5. **The defence names a decision that was wrong**, with the evidence that changed
   the author's mind.

## 2. Artefact-by-artefact notes

### Rerunnable pipeline

The reference implementation splits at output boundaries:
`prepare → featurise → train → evaluate`. `dvc repro` after a parameter change
reruns two stages, not four. The README gives the install command, the train
command, the expected metric, and the tolerance — all written before the final run.

Common gap: an untracked file in the working directory. Clone to a new folder
before submitting, every time.

### Versioned data and model

`data/*.dvc` plus a manifest with supplier, date, rows, columns, and hash. The
artifact metadata records the training data hash, so a model can be traced to a
dataset without asking anyone.

Common gap: provenance recorded in a commit message rather than a file.

### Tests and gate

Five layers, with at least one test per layer that can fail. The gate compares
against a pinned baseline file and prints the failing metric. Three injected
regressions — schema, unit, metric — each fail the correct step.

Common gap: the gate passes because the baseline was regenerated by the same run.
This is the single most common reason a capstone loses gate marks.

### Served endpoint

`/health`, `/ready`, `/predict`, `/model-info`. Five malformed payloads return 422
with the field named. The contract test compares the serving path with the training
path on the same row; reordering the feature list breaks it while the API still
returns 200.

Common gap: a schema that accepts extra fields. The client believes the field was
used.

### Monitoring and alert

A frozen reference from the training window, per-feature PSI, and an alert with an
owner and a first diagnostic step. It fires on the injected batch and not on the
controls. The report separates input drift from accuracy.

Common gap: claiming accuracy fell when only inputs moved. The rubric penalises
this under honesty, not under monitoring.

### Runbook

Deploy, rollback, and the top three alerts, with commands, expected output, and
the failure response. A peer deploys and rolls back in under 30 minutes; rollback
is under five.

Common gap: describing the architecture instead of the procedure.

### Model card and defence

Intended use, limitations with evidence, measured disparity, monitoring plan. The
defence answers "why not simpler?" with a cost avoided, and "what breaks at 10×
load?" with a measured or estimated limit.

Common gap: limitations that are actually humble-brags ("only tested on 600
rows") without saying what that prevents you from claiming.

## 4. Example defence answers

Weak and strong, for the two questions that decide most defences.

**"Why not simpler?"**

> Weak: "The pipeline needs all these stages to be maintainable."
>
> Strong: "I tried a single script first. It took 40 minutes to rerun after a
> parameter change, and I could not tell which stage produced a stale metric. Four
> stages cut the loop to 90 seconds. I kept the registry because rollback had to be
> under five minutes and a file copy could not prove which version was serving."

**"What breaks at 10× load?"**

> Weak: "Kubernetes would scale it."
>
> Strong: "At 200 rps, the single Uvicorn worker saturates at about 40 rps in my
> measurement, so I would need five workers behind the proxy. The model load is
> 1.8 seconds per worker, so a cold start needs a readiness gate. The prediction
> log writes synchronously and would become the bottleneck before the CPU does; I
> would batch or queue it. I have not tested any of this beyond 40 rps."

The strong answers contain a measurement, a specific limit, and an admission.

## 5. Self-marking traps

| Trap | What it looks like | Correction |
|---|---|---|
| Rewarding effort | "I spent three weeks on this" | Score the artefact, not the time |
| Reading the report first | The narrative sets the anchor | Open the rubric, score, then read |
| Counting files as evidence | A folder of screenshots | Ask: could a sceptic use this to verify the claim? |
| Forgiving an untested claim | "It would work in Docker" | Honesty band reflects the gap |
| Inflating the aggregate | One good number, no slices | Slice results decide the evaluation band |
| Ignoring the weakest criterion | Polishing what already scores 3 | The weakest criterion is the next study target |

## 6. If the capstone fails

A fail is usually one of four things, and each has a specific repair:

| Finding | Repair | Time |
|---|---|---|
| Clean clone does not reproduce | Remove the hidden input; document the command | 1–2 days |
| Gate never fails | Pin the baseline; inject a regression; keep the log | 1 day |
| Alert unusable | Add owner, first step, and a control test | Half a day |
| Runbook untested | Have a peer follow it; fix the stalls | 1 day |
| Honesty gap | Rewrite limitations with evidence; label untested parts | Half a day |

The capstone has one submission in a taught course. In self-study, iterate, but
keep the first marked version so the improvement is visible.

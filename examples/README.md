# Lab and project examples

Every file here is material a lab sheet asks you to run. The lab sheets live in
[`docs/labs/`](../docs/labs/index.md); this directory holds the code, the data
generators, and the reference implementations.

Nothing here needs an account, a paid service, or a network connection. The
datasets are synthetic and generated locally.

## What is here

| Path | What it is |
|---|---|
| `raviride/` | The evolving course project: pipeline, registry, service, container, CI, scheduler, drift monitor |
| `labs/lab-01-.../` … `labs/lab-20-.../` | One directory per lab: starter files, a data generator, and an acceptance checker |
| `labs/_shared/` | The tiny assertion harness and the synthetic data generators the kits share |
| `solutions/` | Reference solutions, one directory per lab. Keep them closed until you have attempted the lab |
| `requirements-labs.txt` | The pinned toolchain every kit was executed against |

## Setup, once

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\Activate.ps1
python -m pip install -r examples/requirements-labs.txt
```

Docker is used only by Lab 12, and only when it is installed. Kubernetes is not
required by any lab.

## Running a lab

Every lab follows the same rhythm:

```bash
cd examples/labs/lab-03-data-defects
python make_batches.py               # generate the data (or the defective drop)
python validate.py data/bad_batch.csv   # your work
python check_lab03.py                # objective acceptance checks
```

The checker prints a table and exits `0` only when every check passes. The lab
sheet lists what each check means; the checker is the same standard, not a
different one.

## Verify the whole collection

```bash
python examples/labs/verify_all.py             # all 20 labs
python examples/labs/verify_all.py --only 07 09
```

The runner copies each kit into `labs/.verify/lab-NN/`, overlays the reference
solution from `examples/solutions/`, generates the data, and runs the checker.
Nothing in the lab directories is modified, so this is safe to run while you
are working. It refuses to start if the interpreter is missing a dependency
that a lab needs, rather than reporting a misleading failure.

Last full run: **20/20 labs verified**, Python 3.12 on Windows 11, with a clean
environment created from `examples/requirements-labs.txt`. Lab 12 reports a
static Dockerfile audit, not an image build, because Docker was not installed in
the authoring environment; see [its page](../docs/labs/lab-12-docker-image.md).

## The shared project

`raviride/` is the project Modules 05–14 build in stages. It is deliberately
small: about 900 lines of Python, a DVC graph, two GitHub workflows, a Dockerfile
and a registry policy.

```bash
cd examples/raviride
python -m pip install -e ".[dev,serve]"
python scripts/generate_trips.py --out data/raw/trips.csv
dvc init --no-scm           # this copy lives inside the course repository
python run_pipeline.py
python registry/registry.py train baseline --set-json '{}'
python registry/registry.py promote 1
python -m pytest
```

Measured on Windows 11 with Python 3.12.10: 1,200 rows, 896 train / 304 test,
8 validation checks, MAE 2.7686, 10 tests passed, pipeline about 13 seconds.
The registry steps exercise the `champion` alias; without them the service and
tests use `models/model.joblib` as a fallback and report `"alias": "none"`.
See [the project README](raviride/README.md) for exact output and serving steps.

`--no-scm` is only because this directory is not its own Git repository. In your
own project, `dvc init` is the correct command.

## Data

All data is generated by script and is intentionally small:

| Generator | Rows | Used by |
|---|---|---|
| `raviride/scripts/generate_trips.py` | 1,200 trips | Modules 04–14, the container lab |
| `labs/_shared/make_sessions.py` | 480 study sessions | Labs 01, 02, 07, 10, 11, 13 |
| `labs/lab-16-orchestration/make_data.py` | 1,800 dated sessions | Lab 16 |

Regenerating with the same seed produces byte-identical files, which is what
makes the versioning and drift labs possible.

## Solutions

`solutions/` mirrors the lab ids. Each directory contains the files that satisfy
that lab's checker. They are reference implementations for self-assessment and
for tutors, not a shortcut: several labs are diagnosis exercises where reading
the answer removes the exercise.

## What is not verified here

Three things cannot be executed on a machine without the relevant software, and
each lab says so in its own words:

- **Docker** (Lab 12): the Dockerfile is audited statically and the image build
  is reported as skipped, never as passed.
- **GitHub-hosted runners** (Labs 14 and 15): workflows are linted and their
  `run:` commands are executed locally; the hosted service is not simulated.
- **Kubernetes** (optional extension in the capstone): not required by any lab.
